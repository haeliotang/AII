# ADR-0001：开源边界

- 状态：**提议**（待发起方 Inceptless 确认）
- 日期：2026-10-31
- 决策者：Inceptless
- 相关：[开发文档](../DEVELOPMENT.zh-CN.md) §1.5、M1、M9 · [State & Action Protocol](../../specifications/state-action-protocol.zh-CN.md) · [Viability & Expansion](../../specifications/viability-expansion.zh-CN.md) §7

## 1. 背景

1. 本仓库自 2026-10-28 起公开，声明采用 Apache-2.0。已经发布的内容所授予的许可不可撤回，因此讨论的是**今后**哪些部分开源、哪些可以不开源。
2. 项目的研究方法依赖外部参与：契约要请外部读者找反例（M1.8），H1 实验要求有外部贡献的用例（M3.3），关键结论要能由第三方复现（M8）。
3. 三份契约本质上是标准，只有被他人采用才有价值。
4. Poieweave 的目标是参与物理设备的维护与生产。动作能否被授权、派发、判定为已完成，这些逻辑如果闭源，就无法被外部审计。
5. Inceptless 是公司，需要可持续的商业路径。Inceptless 的其他产品目前以闭源方式发布；Poieweave 采用不同策略的理由见 §3 的驱动因素 D1 与 D3。
6. 从 M9 起，项目会接触客户现场数据、设备厂商的专有协议和第三方许可的模型或数据。

## 2. 决策驱动因素

| 编号 | 因素 | 含义 |
| --- | --- | --- |
| D1 | 可验证性 | 外部能否构造反例、重跑实验、检查结论 |
| D2 | 可采用性 | 契约和核心能否被其他组织采用为接口 |
| D3 | 安全可审计 | 影响物理动作的逻辑能否被审查 |
| D4 | 商业可持续 | 发起方能否长期投入维护 |
| D5 | 保密与合规 | 客户数据、厂商协议、第三方许可能否得到尊重 |
| D6 | 维护负担 | 两套代码之间的同步成本 |

## 3. 选项

| 选项 | 说明 | D1 | D2 | D3 | D4 | D5 | D6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A 全部开源 | 所有代码、模型、适配器、服务都开源 | 好 | 好 | 好 | 差 | 差：厂商协议与客户校准数据无法放入 | 好 |
| **B 开放核心** | 规范、核心与全部安全语义开源；部署、托管与客户特定部分可以不开源 | 好 | 好 | 好 | 中 | 好 | 中 |
| C 只开放规范 | 契约公开，实现闭源 | 差：无法复现 | 中 | 差 | 好 | 好 | 好 |
| D 收回闭源 | 停止公开 | 差 | 差 | 差 | 中 | 好 | 好；且已发布版本无法收回 |

## 4. 决定

采用 **B 开放核心**，并以下列不变式约束。不变式优先于边界表：两者冲突时，按不变式执行。

### 4.1 不变式

- **I1 规范全开放**：所有契约、模式定义、协议、报告格式、场景格式都开源。
- **I2 安全与权责语义全开放**：凡是决定以下问题的代码都必须在开源核心中：动作能否通过校验、授权、派发前复核，以及何时判定为已验证；仿真隔离；证据过期；守恒校验；命令所有权与租约。闭源组件只能让这些检查**更严**，不得放宽、绕过或替换。
- **I3 不削弱**：开源版必须能独立运行所有公开场景的全部流程。不得为了推动商业版本而移除已经开源的能力。
- **I4 安全修复同步**：影响开源核心的安全修复必须进入开源版，可以在协调披露期结束后公开，但不得只提供给闭源版本。
- **I5 证据公开**：支撑项目公开声明的实验，其登记、复现清单与结果必须公开。依赖不可公开数据的结论，不得作为项目的公开声明；如需引用，必须标注"数据不公开，不可外部复现"。
- **I6 只走公开接口**：闭源组件只能通过公开契约定义的接口与核心交互。核心中不得出现只供闭源组件使用的私有接口。

### 4.2 边界表

| 组件 | 归属 | 理由 |
| --- | --- | --- |
| `specifications/` 全部契约 | 开源 | I1 |
| `crates/poie-ontology`、`poie-state`、`poie-sim`、`poie-viability` | 开源 | I2、D1 |
| `crates/poie-runtime`（本地运行时） | 开源 | I2：派发、复核、恢复都在这里 |
| `python/poie_models` 中的通用过程模型 | 开源 | D1；模型结构可审查 |
| 基于公开标准的参考适配器（Ditto、BaSyx/AAS、ROS 2、Open-RMF 等） | 开源 | D2 |
| `scenarios/`（合成数据或许可允许再分发的公开数据） | 开源 | I5 |
| `experiments/`（登记、清单、结果、报告） | 开源 | I5 |
| 故障注入工具、测试、基准 | 开源 | D1、I2 |
| 设备厂商专有协议的适配器（受保密协议或第三方许可约束） | 可闭源 | D5；接口仍走公开契约（I6） |
| 用客户数据或授权数据校准的模型参数 | 可闭源 | D5 |
| 托管服务、多站点运维控制台、企业身份集成 | 可闭源 | D4 |
| 部署配置、支持与认证服务 | 可闭源 | D4 |
| 客户现场数据、凭据、未脱敏日志 | **不进入任何代码仓库** | D5 |
| 操作与研究界面（TypeScript） | 待定，需单独 ADR | 涉及授权交互，可能落入 I2 |
| 商业求解器集成 | 待定，需单独 ADR | 开源核心必须能只用开源求解器工作（I3） |
| 物理试验台的硬件设计文件 | 待定，需单独 ADR | 若开放，考虑 CERN-OHL 系列许可证 |

### 4.3 判定新组件的规则

新组件按顺序回答以下问题，第一个"是"决定归属：

1. 它是否影响安全或权责语义？→ **开源**（I2）
2. 它是否是某项公开结论的证据？→ **开源**（I5）
3. 它是否受第三方保密或许可约束？→ **可闭源**，接口仍须公开（I6）
4. 它是否只对特定客户或部署有价值？→ **可闭源**

都不是：**默认开源**。选择闭源的组件，必须在 PR 或 ADR 中写明依据哪一条。

## 5. 配套措施

| 措施 | 内容 | 时机 |
| --- | --- | --- |
| `NOTICE` 文件 | 按 Apache-2.0 §4(d) 列出版权与归属声明 | 立即 |
| 贡献方式：DCO | 贡献者在提交中签署 `Signed-off-by`（Developer Certificate of Origin），不要求签 CLA | M1.7 |
| `SECURITY.md` | 协调披露渠道与流程；明确安全问题不得在公开 issue 中报告 | M1.7 |
| 依赖许可检查 | CI 中加入 `cargo-deny`：核心只接受与 Apache-2.0 兼容的许可（MIT、BSD、Apache-2.0、ISC、Zlib 等）；MPL-2.0 需逐项记录；GPL / AGPL 不得进入核心 | M1.6 |
| 商标 | Apache-2.0 §6 不授予商标权。名称已定为 Poieweave（ADR-0002）；完成商标检索后注册，并发布 `TRADEMARKS.md`：允许描述性使用，禁止让人误认为 fork 或衍生品是官方版本 | 商标检索之后 |
| 场景数据来源 | 每个场景的 README 注明数据来源与许可；不明来源的数据不得合入 | 立即，Base-01 已满足（全部合成） |
| 合规复核 | 在接触具体设备与客户之前，复核出口管制与行业法规对工业控制软件的要求 | M9 之前 |

**为什么用 DCO 而不是 CLA**：Apache-2.0 本身已允许 Inceptless 在闭源产品中使用开源贡献，因此 CLA 不是商业路径的必要条件。DCO 的门槛更低，更有利于 D1。代价是：将来如果想把核心改为更严格的许可证，需要取得所有贡献者的同意，实际上不可行。本决定接受这一代价。

## 6. 后果

**正面**：

- 外部可以审查、反驳和复现，研究方法的前提得到满足；
- 契约有机会成为跨组织的接口；
- 影响物理动作的逻辑始终可审计；
- 客户与厂商的保密要求有明确的落脚点。

**负面**：

- 任何人（包括竞争者）都可以直接使用开源核心；Inceptless 的差异化只能来自部署能力、服务、校准数据和可信度，而不是核心算法；
- 维护公开社区（评审、issue、文档）需要持续投入；
- 闭源组件必须跟随开源核心的接口演进，产生同步成本；
- 不变式 I2 限制了商业版本的设计空间：涉及安全语义的改进必须先进开源核心。

## 7. 推翻条件

出现以下情况时，应当写新的 ADR 重新评估（已发布的开源内容在任何情况下都不收回）：

1. 商业部分长期无法覆盖维护成本：评估扩大**未来新组件**中可闭源的范围，不变式 I1–I6 保持不变；
2. 外部贡献与外部复现长期为零，"开源对研究方法有价值"这一前提没有兑现：复盘原因，但不默认转向闭源；
3. 开源核心被用于明显危害安全的部署，且许可证与商标手段都无法约束：评估治理措施（例如发布安全使用指南、拒绝为该部署提供认证）。
