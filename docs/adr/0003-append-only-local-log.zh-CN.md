# ADR-0003：本地只追加日志的存储选型（M4.2）

- 状态：**已接受**（2026-10-31，作为 M4.2 的实现依据）
- 决策者：项目维护者（技术选型，不涉及开源边界；开源边界见 ADR-0001）
- 相关：[State & Action Protocol](../../specifications/state-action-protocol.zh-CN.md) §1、§5 · [开发文档](../DEVELOPMENT.zh-CN.md) M4.2、§1.5

## 1. 背景

SAP §1 要求记录只追加：写入后不得修改或删除，更正以新记录表达。§5 要求"先持久写入日志，再产生外部效果"。M4.2 需要一个本地持久化实现，满足：

- 单进程写入时的原子性：崩溃后要么整条记录存在，要么不存在；
- 记录按场址序号（`<site>/<seq>`）单调递增；
- 能按场址顺序读取全部记录，供投影与重放；
- 崩溃恢复语义可测试（M4.7 将覆盖每个写入点）；
- 单机、无服务端、无网络（网络属于 M12）。

开发文档原先把 SQLite 列为候选，并要求选型走 ADR（§1.5：引入运行时依赖必须写 ADR）。

## 2. 选项

| 选项 | 说明 | 原子性 | 依赖与许可 | 重放/移植 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 单文件 JSON Lines + fsync** | 每条记录一行 JSON，`write_all` 后 `sync_data`；启动时截断尾部不完整行 | 单条追加 + fsync；尾部残行可丢弃 | 仅 `serde` / `serde_json`（MIT OR Apache-2.0） | 人可读、可逐行重放、可 diff | **采用** |
| B SQLite（`rusqlite`） | 关系存储、事务、索引 | 事务保证 | 引入 C 依赖、构建复杂度、许可检查 | 需要 schema 与迁移 | 推迟 |
| C 嵌入式 KV（redb / sled） | Rust 原生、无 C | 事务/原子批 | 新依赖、格式无长期承诺 | 需要编码层 | 推迟 |
| D 仅内存 | 开发期最快 | 无持久性 | 无 | 不可重放 | 不满足 §5 |

## 3. 决定

采用 **A：单文件 JSON Lines 只追加日志**，并遵守：

1. 一条记录一次 `write_all(line + '\n')`，随后 `sync_data`；不提供修改或删除接口。
2. 追加时校验场址序号严格递增（同一场址的新记录 `seq` 必须大于上一条）。
3. 打开时逐行解析；只允许**最后一行**不完整（崩溃留下的残行），此时截断到最后一个完整行；中间行损坏报错，不静默丢弃。
4. 记录以 serde 序列化为 JSON；字段名与 `crates/poie-state` 的类型一致，便于第三方审计与重放。
5. 存储实现藏在最小 API 之后（`create/open/append/records/records_for_site/last_seq`）；后续替换存储不应改变协议层接口。
6. **序号不复用**（2026-11-01 补充，issue #111）：第 3 条只处理尾部残行，不覆盖整段丢失与快照回滚。回滚后本地日志看不到已经发出的序号，若继续编号就会复用 `<site>/<seq>`（评审 B-06）。因此：
   - 新增 `high_water/raise_high_water`：从对端学到的本场址序号高水位写入日志旁的 `<log>.hwm` 文件（临时文件 + `sync_data` + rename），打开日志时读回；追加必须大于"日志最大序号与已学高水位"中的较大者；
   - `.hwm` 与日志同介质，整盘或虚拟机快照回滚时可能一并丢失，因此它只缩小风险，不消除风险。兜底是 SAP §6.4 第 3 条：重连对账发现同一 `record_id` 内容不同即报 `sequence_collision`（`poie-federation` 已实现）；
   - 未采用评审建议的 `incarnation` 字段（`record_id = <site>/<incarnation>/<seq>`）：它要改动记录信封与所有已提交的实验产物，而"不复用 + 碰撞检测"已能满足 SAP §2.1 的唯一性要求。若现场证明回滚常态化、碰撞频繁，再按第 5 节另写 ADR。

新增两个运行时依赖：`serde`（工作区已在用）与 `serde_json`（MIT OR Apache-2.0，均符合 ADR-0001 §5 的许可策略）。

## 4. 后果

- 崩溃安全：尾部残行在下次打开时被截断；已确认的写入不会丢失（受文件系统与 fsync 语义约束）。
- 无索引、无并发写保护：单进程单写入者的假设必须由调用方保证；多进程写同一文件不在本实现范围。
- 日志体积随时间增长；压缩与快照属于 SAP §10 待决问题（M4 之后）。
- 回滚（快照恢复、整段丢失）不能由单文件格式本身防住：本地只能靠 `.hwm` 与重启后向对端取回本场址记录（SAP §5 第 5 条），最终由对账的 `sequence_collision` 发现（§3 第 6 条）。
- JSON 明文可被人工检查，但也意味着不能存放秘密；SAP 与 ADR-0001 本就要求"客户数据与凭据不进入代码仓库"。
- 写入性能受 fsync 限制；M4 的单机实验规模（Base-01）远低于该上限。

## 5. 推翻条件

出现以下任一情况时重新评估（新 ADR）：

1. 需要多进程或多写入者并发追加；
2. 日志规模或读取模式需要索引、范围查询或快速启动（如引入快照机制）；
3. 崩溃注入测试发现当前格式无法区分"完整写入"与"部分写入"的边界情况；
4. 需要跨场址日志交换（M12）时，若 JSON Lines 的合并与因果排序代价过高。
