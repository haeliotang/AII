**Autonomous Infrastructure Intelligence · 自主基础设施智能**

版本：0.1 / 2026-10-28

状态：研究提案与文献级架构审查，尚无实现、实验结果或现场验证。

## 1. 使命与问题边界

为能够自主运行、维护、生产并逐步扩展自身能力的工业系统，建立开放的软件基础。

Poieweave 的长期问题是：在资源有限、外部通信与补给间歇中断、设备持续损耗的情况下，一个物理系统能否维持关键服务、恢复生产，并降低对外部支持的关键依赖？

这需要把能源、水、材料、制造、机器人、物流、库存、维修与人类授权连接成可计算的整体。跨星球工业是远期应用边界；离网设施、偏远工厂与受控实验基地提供可验证的地球环境。本文不预测跨星球文明的实现年份，也不把软件能力等同于硬件制造能力。

平台目标分为三个层次：自主运营、自主维护、自主工业扩张。第三层要求新增设施通过检验、能够投入使用，并在扣除建造与维护成本后产生净能力增益。电子器件、精密加工、催化剂、计量与工艺知识等外部依赖必须被明确记录，不能假设工业链天然闭环。

## 2. 证据等级与本轮审查范围

本文使用三类陈述：

- **已查阅事实**：官方文档明确描述的项目职责，附来源。
- **架构提案**：Poieweave 拟采用的模型、边界与实现方式，尚待验证。
- **研究假设**：可被实验推翻的能力或性能判断。

本轮审查基于官方项目说明与架构文档，未进行源码级审计、依赖版本锁定、编译、部署或接口互通测试。因此，“适合作为候选组件”不等于“可以直接拼接”。此前讨论中的具体 SDK 成熟度、发行版兼容性和性能判断不作为本轮已证实结论。

### 2.1 组件职责与边界

| 项目 | 官方资料支持的职责 | Poieweave 的候选使用方式 | 必须进一步验证的边界 |
| --- | --- | --- | --- |
| NASA ISAAC [1][2] | 将设施数据与自主机器人结合，研究航天设施自主照护 | 参考设施异常到机器人任务的闭环与数据组织 | 运行环境、任务接口、依赖版本、可独立复用范围；与 NVIDIA Isaac 区分 |
| Open-RMF [3] | ROS 2 生态中的任务队列、共享资源调度与机器人舰队适配 | 承接已经通过 Poieweave 资源与权限检查的任务 | 取消、失败、重试、部分完成、能源预算以及任务结果的回传语义 |
| Eclipse Ditto [4] | IoT 数字孪生与设备交互抽象 | 接入设备状态、属性与消息 | 状态新鲜度、连接拓扑、断网恢复；命令接收不可等同于物理执行完成 |
| IDAES [5] | 工业过程模型、流程建模与优化工具 | 提供物料、能量与工艺约束求解 | 特定工艺模型是否存在、校准数据、动态边界、求解收敛和计算预算 |
| Eclipse BaSyx [6] | 基于 AAS 的工业资产数字孪生及互操作基础设施 | 资产身份、属性与子模型的兼容映射 | 选定 AAS 版本、子模型、单位和 Poieweave 能力语义之间的映射 |
| Palantir Ontology [7] | 连接运营对象、关系与行动等语义 | 借鉴状态、逻辑、行动和权限的一体化设计 | 仅作为架构参考；不假定其缺乏物理模型或场景分析，也不引入产品依赖 |

**审查推论：**上述项目覆盖不同专业边界。Poieweave 值得研究的组合是：跨域物理与能力依赖、带证据的长期可行性评估、断网执行语义，以及生产—维护—扩张闭环。该推论不是市场独占性、算法原创性或不存在替代产品的证明。

### 2.2 为什么通信接通不等于系统集成

水泵出现振动异常、机器人可以运输备件、工艺模型可以预测产水下降，仍不足以自动决定维修顺序。缺失的语义包括：诊断可信度、失效时间范围、库存、零件质量、工具可用性、维修消耗、停机影响、执行授权，以及修复后如何确认供水恢复。

Poieweave 的核心工作是定义并验证这些跨系统语义，而不是让所有组件彼此直接调用。

## 3. 目标架构与权责

| 层次 | 责任 | 输出与边界 |
| --- | --- | --- |
| Mission & Policy | 人类指定关键服务、发展目标、禁止事项与授权范围 | 版本化目标和策略；平台不能自行扩大权限 |
| Planning & Expansion | 比较生产、维护、恢复与扩建方案 | 候选计划及前提、预算、有效期 |
| World & Viability | 预测状态演化，评估服务与恢复路径 | 带场景、模型版本、不确定性的评估 |
| Physical Ontology & Capability Graph | 统一资产、资源、工艺与能力依赖 | 有类型、有时间、有证据的操作模型 |
| Execution & Verification | 检查、派发、追踪、验证动作 | 执行回执和独立结果证据；失败时进入明确状态 |
| Local Runtime | 持久状态、事件重放、恢复与同步 | 本地自治；不把云端连接当作必要条件 |
| Integration & Controllers | 连接设备与专业系统 | 原有控制器、保护和急停保留现场权限 |

这些是逻辑职责，不要求分别部署微服务。初期采用少量本地模块与进程边界；只有真实隔离、性能或部署需求出现时才拆分。

## 4. 物理运营本体与生产能力图

### 4.1 最小概念集合

| 概念 | 关键含义 |
| --- | --- |
| Asset | 有身份与位置的设备，包含健康、可用性与接口 |
| Resource / Inventory | 有单位、批次、质量与数量的物料或储能 |
| Process | 输入、输出、设备占用、时间、损耗和约束 |
| Capability | 在明确条件下完成某类过程的能力 |
| Observation / Estimate / Prediction | 分离观测、推断与预测，并关联来源 |
| Action / Plan | 前置条件、预算、授权、预期效果及验证办法 |
| Goal / Constraint / Policy | 服务需求、物理边界与权限边界 |

物理量必须有单位和量纲；功率与能量、流量与库存不能混用。每条关键记录至少携带来源、事件时间、接收时间、质量状态、模型或模式版本。过期和缺失信息不能自动解释为零或健康。

### 4.2 为什么研究超图

“材料 + 设备 + 工具 + 能源 + 操作能力 + 工艺 + 检验”共同满足，才能产出合格零件。普通二元依赖边容易丢失这种 AND 关系；不同工艺路线之间又存在 OR 选择。

拟研究有类型、时间和物理约束的生产能力超图。首版可以用显式过程节点与输入/输出边实现，不必先采用专用图数据库。图可达性只负责生成候选路线，不能证明工艺可行。

必须处理：

1. 消耗性物料与可重复使用设备的区别，避免把同一库存或机器重复分配。
2. 工序顺序、设备容量、加工精度、合格率、工具磨损和检验约束。
3. 循环维修依赖：制造替换机器所需的唯一机器已经故障时，不能判定可自修复。
4. 替代工艺的条件差异，以及启动库存、启动能源和外部零件需求。
5. 未知能力与已验证能力分离；“模型里存在一条路线”不等于“现场已能完成”。

### 4.3 贯穿示例

水泵 P1 退化。可以使用库存备件直接维修，也可以加工替代零件，但后者占用车床、能源、材料与检验资源。若维修机器人和车床同时依赖即将停机的电源，则分别可行的子任务可能无法联合完成。

Poieweave 应输出可行路线及其资源占用、最晚启动时间、证据和未解决依赖；若不可行，明确指出阻断条件。不得用一段自然语言建议替代计算证据。

## 5. 世界模型与长期可行性

用离散时间示意模型表达研究边界：

`x[t+1] = F(x[t], u[t], w[t]; theta)`

其中状态包含库存、设备健康、在途任务与生产能力；行动包含调度、维修、加工和建设；扰动包含故障、环境变化和补给中断；参数携带校准版本与适用范围。真实系统可以混合连续过程与离散事件，不能默认单一时间步长足以描述所有控制层。

模型体系组合守恒方程、工艺求解、离散事件、可靠性模型和经验证的数据模型。LLM 可以辅助建模与生成候选方案，不能作为质量守恒或设备执行成功的唯一判断者。

### 5.1 有限时域可行性定义

给定时域 H、安全与服务约束集合 K、扰动轨迹集合 W，以及非预知未来的策略集合 Π，研究：

`V_H = {x0 | exists pi in Π, for all w in W, x_t(pi,w) in K for every t = 0..H}`

策略只能使用当时可获得的观测；不能根据未来故障“提前知道答案”。部分可观测状态需要状态集合或信念状态，不能把真实隐藏状态直接交给规划器。

这是有限时域、指定模型与扰动集合下的鲁棒可行性定义。大规模工业系统通常只能计算近似、界或场景证据。抽样场景全部成功既不证明无限时域可生存，也不证明未抽样扰动下安全。求解超时或未找到解也不等于数学上的不可行。

### 5.2 四组独立指标

| 维度 | 可操作指标 | 报告约束 |
| --- | --- | --- |
| 生存能力 | 关键服务维持时长、约束违反、可行恢复路径 | 标注时域、策略、模型与场景集合；超过观测窗口按截尾记录 |
| 独立性 | 各资源外部输入量、关键进口备件清单、本地替代覆盖 | 各单位分开；同时计入上游工艺、质量与工具依赖 |
| 韧性 | 服务损失积分、恢复时间、传播范围 | 说明服务优先级、恢复判据和失败案例 |
| 可持续性 | 净消耗、回收损失、设备退化、长期库存趋势 | 不以停掉全部生产制造“高分”；公开核算边界 |

规划优先满足安全与最低服务约束，再比较可行方案的长期服务、维修与发展效果。权重或词典序由人类策略显式规定。模型发现不可行时报告冲突及受控降级方案，不擅自放宽硬约束。

## 6. 状态与行动协议提案

### 6.1 事实与意图隔离

观测、状态估计、预测、期望状态和动作回执是不同记录。下发“关闭阀门”不代表阀门关闭；接收 ACK 也不代表工艺后果已实现。

建议动作生命周期：`proposed -> validated -> authorized -> dispatched -> acknowledged -> verified`，另设 rejected、expired、failed、cancelled 和 outcome-unknown 等终态或待处置状态。具体状态机尚未冻结。

动作至少关联 action_id、目标资产、计划与策略版本、前置状态版本、有效期、资源预算、幂等键、授权范围和验证要求。执行前再次检查时效与现场状态，不能仅依赖计划生成时的检查。

### 6.2 网络分区与恢复

现场保存必要模型、策略、事实与事件日志。分区期间单个资产保留明确的命令所有权；不能让两个断联节点分别花掉同一份库存或同时控制同一执行器。

重连时同步事实和因果关系，对冲突做显式处理。过期动作不自动重放；遥测可合并并不意味着物理命令可用“最后写入胜出”。使用持久命令记录、接收端去重与现场对账降低重复执行风险，但不宣称通用端到端 exactly-once。

执行结果不明时先查询或检查现场，不盲目重试不可逆动作。进程崩溃、ACK 丢失、设备重启和时钟偏差都必须成为测试场景。

### 6.3 模拟与权限隔离

仿真分支拥有独立命名空间和无现场权限的连接。求解器只返回候选计划与证据；执行权限由运行时管理。最底层保护、硬件急停和确定性控制不依赖 LLM 或远程服务。

## 7. 技术栈决策与取舍

**提案：Rust-first，而非 Rust-only。**

| 边界 | 方向 | 原因与代价 |
| --- | --- | --- |
| 身份、单位、图、事件、计划与动作状态机 | Rust | 显式类型、内存与并发约束；不能替代物理正确性和时序验证 |
| 工艺与数学优化 | Python / IDAES 等专业求解工具 | 复用科学模型；需要版本化协议、超时与结果验证 |
| 机器人适配 | ROS 2 生态优先，C++ 或成熟绑定 | 跟随上游支持环境；Rust 绑定兼容性必须单独核查 |
| 操作与研究界面 | 后续按需要采用 TypeScript | 与执行权分离；首版不必先做完整控制台 |

Tokio、SQLite、Zenoh、DataFusion 和 Wasmtime 等仅作为后续候选，不构成当前依赖承诺。先以本地持久化与可重放模型验证语义，再决定网络、查询和插件技术。服务间采用明确的模式版本、单位、错误分类、截止时间与结果摘要。

本轮不创建 Cargo 空工程，不安装第三方组件，也不把研究文档中的候选依赖写成已完成集成。

## 8. 首个研究环境：Autonomous Base-01

目标是包含能源—生产—损耗—维护—恢复的最小完整虚拟工业闭环。

组成：发电、储能、水处理、材料与备件仓库、简单加工设备、物流能力、维修能力。机器人早期作为有时间、耗能和可用性约束的执行资源建模；不要求先实现完整三维机器人仿真。

扰动包括：发电下降、水泵退化、备件缺失、设备共同故障、任务延迟、观测过期、传感器偏差、通信中断，以及修复失败。场景参数是明确标注的合成假设，之后再用公开或授权数据校准。

### 8.1 可证伪假设

- H1：联合能力与资源依赖模型能够识别独立设备调度遗漏的恢复阻断条件。
- H2：在相同信息和计算预算下，联合长期规划能在部分预先定义的扰动分布上改善服务保障，同时保持约束满足。
- H3：本地持久执行协议能在规定的崩溃和网络故障模型下避免已测试类别的重复物理动作，并保留可对账状态。
- H4：新增生产能力的收益在扣除建造、检验、维护和关键外部投入后仍可能为正。

这些是假设，没有已有性能数字。若实验不支持，应修正模型或方法，并保留负结果。

### 8.2 对照与消融

比较任务优先级策略、带安全库存的规则策略、短期资源优化，以及 Poieweave 联合策略。统一初态、观测权限、动作集合、设备模型、故障轨迹和计算预算；以独立留出场景评估，并公开开发阶段与最终评估的划分。

有状态相关故障时使用共同外生随机源与同一故障机制，而不是强迫不同使用历史下的设备在相同瞬间故障。固定轨迹故障与状态相关故障分开报告。

逐项移除长期时域、退化模型、能力依赖和重新规划，识别收益来源。报告全部运行、随机种子、失败、超时、不可行与置信区间；有限样本不证明鲁棒保证。

### 8.3 验收证据

| 项目 | 判据 |
| --- | --- |
| 守恒与单位 | 每次状态转移核算输入、输出、存储变化与损耗；容差按量纲及求解精度预先规定 |
| 可重放 | 固定事件顺序、模型版本和随机种子可重建状态；浮点比较采用明确容差 |
| 依赖正确性 | 覆盖循环维修、缺少启动资源、共享设备、质量不合格和替代工艺案例 |
| 求解边界 | 区分可行、已证不可行、超时、数值失败和未知；不把未知当作安全 |
| 协议恢复 | 故障注入覆盖 ACK 丢失、重复消息、崩溃重启、过期授权与断网恢复 |
| 实验复现 | 保存输入哈希、版本、参数、策略、种子、求解设置、原始结果与指标定义 |

具体阈值随第一个正式场景规范预注册；本文件不虚构未运行的验收结果。

## 9. 路线与阶段门槛

| 阶段 | 交付目标 | 进入下一阶段的条件 |
| --- | --- | --- |
| Foundation | ontology + graph 原型、状态协议、Base-01 | 守恒、依赖反例与重放通过，能够描述完整虚拟闭环 |
| Autonomy | 生产—维护—恢复联合规划与可行性报告 | 公平基线、消融与留出场景；结论及负结果可复现 |
| Embodiment | 适配器、只读影子运行、受控实体试验 | 物理反馈验证、故障恢复、现场保护与操作者接管均经过验证 |
| Expansion | 新增制造能力与替代供应链规划 | 可实施、可检验且核算后净能力增加；未闭合依赖明确 |
| Federation | 多基地协作、资源交换与知识共享 | 网络分区不破坏本地权责，跨站承诺可对账 |

此前讨论的 2026–2036 可作为愿景时间窗口，而不作为交付承诺。本文采用证据门槛驱动推进；不因年份到达就宣称进入下一阶段。

优先起草三项契约：Physical Ontology、State & Action Protocol、Viability & Expansion Contract。先做可反驳的小规范和参考场景，经实验后再稳定接口，不在实现前冻结大而全的标准。

## 10. 开放研究与治理

当前仓库只包含 README 与本研究文档。未来目录按实际需要增加：`crates/` 放 Rust 核心，`specifications/` 放协议，`scenarios/` 放可复现实验，`adapters/` 放边界集成；不提前制造大量空模块。

架构调整应记录动机、替代方案和验证证据。研究结果区分探索、待复现与已复现；任何“优于基线”“完成自主维护”“实现扩张”的声明都链接到具体运行记录。

## 11. 核心未解问题

1. 哪一种最小能力语义能同时描述制造、维修、替代和扩建，而不过度抽象？
2. 何种规模下可以得到可用的可行域近似，如何报告保守性与漏判？
3. 如何区分模型误差造成的不可行与真实物理不可行？
4. 何种检验证据足以把“预测能力”升级为“可用能力”？
5. 网络分区时，跨站库存与任务承诺采用何种所有权机制？
6. 什么情况下应停止扩大平台范围，先修复模型、数据或实验设计？

若模型不守恒、基线比较不公平、状态证据无法重建、或者现场反馈无法确认，就暂停能力扩展并修复相应基础。这是研究有效性的门槛，不是对远期愿景的缩减。
