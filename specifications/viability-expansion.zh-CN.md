## 0. 目的与范围

本契约规定两类判断应当如何提问、如何作答、如何报告：

1. **可行性**：在给定时域、约束、扰动和策略类下，关键服务能否维持、能维持多久、能否恢复。
2. **扩张**：新增一项生产能力，在扣除建造、检验、维护和外部输入之后，是否带来净能力增益。

本契约不规定求解算法，只规定输入、结论类别、指标定义和证据要求。规范用语同 Physical Ontology §0.1。

## 1. 原则

1. **没有通用自主分数**：四组指标（§4）必须分开报告，不得合成为单一分数。
2. **结论带条件**：每个结论必须附带时域、约束集、扰动集、策略类、模型版本、计算预算和方法类型。脱离这些条件的结论无效。
3. **区分"没找到"和"不存在"**：求解超时、数值失败或抽样未覆盖，不得被报告为不可行或安全。
4. **硬约束不自动放宽**：发现不可行时，报告冲突和受控降级选项，由人类策略决定。
5. **模拟不是物理证明**：仿真结论的最高证据等级是 `modeled`；要升级到 `demonstrated` 或 `verified`，需要现场记录（Physical Ontology §3.5）。

## 2. 可行性查询

### 2.1 数学定义

给定时域 H、约束集合 K、扰动轨迹集合 W、非预知策略类 Π，研究的可行集为：

`V_H = { x0 | ∃ π ∈ Π, ∀ w ∈ W : ∀ t ∈ 0..H, x_t(π, w) ∈ K，且 x_H(π, w) ∈ K_T }`

非预知的含义是：策略在 t 时刻只能使用 t 时刻之前可获得的观测，不能根据尚未发生的扰动作决定。部分可观测时，策略的输入是信念状态或状态集合，不是真实隐藏状态。

**终端条件**：有限时域必须同时给出终端约束 `K_T`（例如关键库存、储能与关键资产健康在 H 时刻不低于某个安全水平），由人类策略声明并版本化。否则，策略可以在 H 时刻把库存或电池用尽而不被任何指标发现。不设终端约束时，查询必须显式写明"无"及理由。无论是否设约束，报告都必须给出每个场景在 H 时刻的终端状态：关键库存、储能、关键资产健康，以及仍未恢复的服务缺口（§4.3）。

**非预知性必须可检查**。评估只检验具体的策略，下列三条缺一不可：

1. 同一个策略实例（相同参数与配置）在全部场景上运行，不得逐场景重新优化或调参。逐场景、看得到整条扰动轨迹的开环优化回答的是 ∀w∃π，不是本定义。
2. 策略在 t 时刻的输入只能是截至 t 的投影状态（SAP §2.3 的状态版本）或观测。
3. 报告附带决策记录：每次决策的时刻、所用状态或观测的截止时刻、策略实例标识。任何一次决策用到了晚于决策时刻的信息，或不同场景使用了不同的策略实例，报告即无效。

被测策略失败，只说明这个策略失败；由 ∃π 的定义，它不能推出 `x0 ∉ V_H`（§3.1 `counterexample`）。

### 2.2 查询字段

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `initial_state` | 必须 | 状态版本（SAP §2.3）或场景初态的哈希 |
| `horizon` | 必须 | 时域 H，时间量纲；离散步长或事件语义必须同时声明 |
| `services` | 必须 | 关键服务列表及各自的最低服务水平 |
| `hard_constraints` | 必须 | 安全约束与物理边界 |
| `disturbances` | 必须 | 扰动集合的定义，见 §2.3 |
| `policy_class` | 必须 | 策略类：规则名、规划器名与参数、重规划频率、可用观测，以及在全部场景上运行的策略实例标识（§2.1） |
| `terminal` | 必须 | 终端约束 `K_T`；不设时写明"无"及理由（§2.1） |
| `models` | 必须 | 所用模型的标识、版本与适用范围 |
| `min_verification` | 必须 | 规划可使用的工艺最低验证等级 |
| `budget` | 必须 | 计算预算（墙钟时间、迭代或样本数） |
| `method` | 必须 | 方法类型，见 §3.2 |
| `seeds` | 抽样方法必须 | 随机种子；运行前登记（§7） |

### 2.3 扰动集合

扰动集合必须以可复现的方式定义，并区分两类：

- **固定轨迹扰动**：事先给定发生时刻的事件（"第 30 小时母线故障"）。
- **状态相关扰动**：发生率依赖状态与使用历史的事件（"泵的故障率随振动等级上升"）。在不同策略之间对比时，必须使用共同的外生随机源和同一故障机制，而不是强迫不同使用历史下的设备在同一时刻故障。

两类结果必须分开报告。扰动参数若是合成假设，必须标注 `synthetic`。

比较不同的系统配置（例如扩张与不扩张）时，"同一扰动集合"指**共同外生随机源**，而不是"同一组故障对象"：一种配置新增的资产和工艺，要带着自己的故障机制进入它自己的扰动集合（§6.2）。

## 3. 可行性结论

### 3.1 结论类别

| 结论 | 含义 | 必须附带 |
| --- | --- | --- |
| `held_on_tested` | 所有被测扰动下，在 H 内约束均满足 | 被测场景数、方法类型；明确声明不覆盖未测扰动 |
| `counterexample` | 存在被测扰动，使**被测策略**下的约束被违反 | 场景、首次违反时刻、被违反的约束、当时状态、被测策略实例；只否定该策略，不否定 ∃π（§2.1） |
| `infeasible_in_model` | 方法给出了在模型内不可行的证明 | 证明或证书的形式与可检查方式 |
| `timeout` | 预算耗尽，未定 | 已完成部分 |
| `numerical_failure` | 求解器数值失败 | 求解器、设置、失败信息 |
| `unknown_input` | 初态或模型输入存在未知量，无法判断 | 未知项列表 |

`held_on_tested` 不得被表述为"可生存""安全"或"鲁棒"。只有当 `method` 是穷举或集合方法、且该方法覆盖了整个 W 时，才可以表述为"在模型与 W 内成立"。

### 3.2 方法类型

| 方法 | 能支持的最强表述 |
| --- | --- |
| `sampled` | 被测场景上成立 / 找到反例 |
| `enumerated` | 在有限 W 上成立 / 找到反例 |
| `set_based` | 在模型与 W 内成立（含保守近似时，须说明保守方向） |
| `certificate` | 在模型内不可行或成立，附可独立检查的证书 |

**方法与结论的兼容关系**（逐场景结论）：

| 方法 | 允许的结论 |
| --- | --- |
| `sampled` | `held_on_tested`、`counterexample`、`timeout`、`numerical_failure`、`unknown_input` |
| `enumerated` | 同 `sampled` |
| `set_based` | 六类均可；`infeasible_in_model` 须说明保守方向 |
| `certificate` | 六类均可；`held_on_tested` 与 `infeasible_in_model` 须附证书 |

`sampled` 与 `enumerated` 只检验有限个场景，不能给出 `infeasible_in_model`；即使全部被测场景都失败，也只能报告 `counterexample`。

**查询级聚合**：逐场景结论必须按下列顺序聚合为一个查询级结论，并同时报告每个类别的场景数：

1. 任一 `infeasible_in_model` → `infeasible_in_model`；
2. 否则，任一 `counterexample` → `counterexample`；
3. 否则，任一未定 → 未定，按 `unknown_input`、`numerical_failure`、`timeout` 的顺序取第一个出现的类别；
4. 只有全部场景都是 `held_on_tested`，查询结论才是 `held_on_tested`。

不得以多数决代替上述规则，也不得只报告有利的子集。

### 3.3 结构层查询

Physical Ontology §6 的能力图查询（`candidate` / `blocked` / `unknown` / `search_limit`）是**无时域的结构层**判断，是可行性分析的必要条件，不是充分条件：

- `blocked` 的恢复目标在任何时域内都无法由本模型完成，可以直接作为可行性分析的反例依据；
- `candidate` 只说明存在一条资源上不冲突的路线，时间、容量、并发和扰动仍需时域分析。

## 4. 四组指标

指标必须针对每个服务、每个场景计算，再报告分布。

- **所有运行都进入分布**：`timeout`、`numerical_failure`、`unknown_input` 的运行不得从分布中剔除。它们在停止（或失去判断能力）的时刻按截尾计入，同时单独列出，并给出敏感性结果：把这些运行视为在停止时刻失效（"按最坏情况计入"）。困难场景越容易让求解器失败，剔除造成的偏差越大。
- **采样与缺失**：报告必须声明服务水平的采样分辨率。缺失读数按 `unknown` 处理，不得按满水平处理：`T_s` 在第一个缺失读数的时刻截尾；建造期检查等逐时刻判据把缺失读数视为未通过；服务损失积分不覆盖无读数的时段，该时段的时长单独报告。

### 4.1 生存能力（Viability）

| 指标 | 定义 | 单位 |
| --- | --- | --- |
| 服务维持时长 `T_s` | 场景开始到服务 s 首次低于最低水平的时间 | 时间 |
| 截尾 | `T_s` 超过 H 时记为截尾 `> H`，不得记为 H | — |
| 约束违反 | 硬约束违反的次数与首次时刻 | 次 / 时间 |
| 恢复路径 | 首次违反时，结构层查询对恢复目标的结论 | 类别 |

报告：最小值、分位数、截尾个数。

- 最小值是已观测失效时刻中的最小者；全部截尾时报"> 最大随访时刻"。
- 分位数必须用处理截尾的估计量在**全部运行**上计算（乘积极限，即 Kaplan–Meier）：分位点 q 取估计累积失效比例首次达到 q 的时刻；估计在随访期内达不到 q 时，报"> 最大随访时刻"（通常为 "> H"），不得报一个数值。不得只在未截尾的子样本上计算分位数：这样会让大多数场景截尾、少数场景早期失效的策略显得比全部中期失效的策略更差。
- 均值只有在没有截尾（含按截尾计入的未定运行）时才可报告。

### 4.2 独立性（Independence）

| 指标 | 定义 | 单位 |
| --- | --- | --- |
| 外部输入量 | 时域内每种资源从外部输入的数量 | 各资源自身单位，分开报告 |
| 关键外部依赖 | 关键服务的候选恢复路线上，所有外部依赖资源（Physical Ontology §6.5） | 清单 |
| 本地替代覆盖 | 关键资源中，存在闭合的本地生产路线的个数（判据见下） | n / m（两个整数，不化为百分数分数），并列出 m 个资源 |

外部依赖必须追溯上游：本地能加工某零件，但刀具或检验量具只能外购，则该刀具或量具也是关键外部依赖。清单必须对关键服务的**全部**候选恢复路线取并集；没有候选路线时，从阻断根因中的外部资源回退生成（实现要求见 Physical Ontology §6.3 规则 15、§6.5）。

本地替代覆盖的判据：

- **分母 m**：关键资源集合自动导出，等于关键服务全部候选恢复路线所消耗的资源，加上上面的关键外部依赖清单。不得手工增删，例如加入几种本地容易生产、但与关键服务无关的资源来抬高比例。
- **分子 n**：把该资源自身的库存视为零之后，能力图仍能找到一条生产一个单位的候选路线，且路线等级（含能力等级，Physical Ontology §6.3 规则 13）不低于 `min_verification`，全部输入在当前库存水平下闭合。只有一道工艺、但它要消耗已经缺货的外购刀具，不算覆盖。
- 每个被计为覆盖的资源，必须同时列出它的本地路线仍在消耗的外部输入（"闭合到给定库存水平"）。

### 4.3 韧性（Resilience）

| 指标 | 定义 | 单位 |
| --- | --- | --- |
| 服务损失积分 | ∫₀ᴴ max(0, 最低水平 − 实际水平) dt，按服务分别计算；无读数的时段不计入，单独报告其时长 | 服务单位 × 时间 |
| H 时刻缺口 | H 时刻仍未恢复的缺口（最低水平 − 实际水平），必须与服务损失积分一起报告；末端读数缺失时报 `unknown` | 服务单位 |
| 恢复时间 | 首次违反到恢复最低水平的时间；未恢复则截尾 | 时间 |
| 传播范围 | 初始故障发生后，受影响的服务数和资产数 | 个 |

必须说明服务优先级和恢复判据，并列出未恢复的案例。只看损失积分会奖励"晚失效、不恢复"：H = 100 h 时，95 h 失效且不恢复的损失积分小于 10 h 失效、30 h 恢复，H 时刻缺口能把前者暴露出来。

### 4.4 可持续性（Sustainability）

| 指标 | 定义 | 单位 |
| --- | --- | --- |
| 净消耗 | 每种资源的期末库存 − 期初库存 − 外部输入 | 各资源单位 |
| 回收损失 | 回收工艺输入与可再用输出之差 | 质量 |
| 设备退化 | 关键资产健康指标的期初与期末对比 | 指标自身单位 |
| 产出 | 时域内各生产工艺的合格产出 | 各资源单位 |

**防作弊条款**：可持续性指标必须与产出和服务指标一起报告。停掉全部生产可以让净消耗接近零，但这不是"更可持续"。

## 5. 决策准则

1. 比较方案时按词典序：先满足硬安全约束，再满足关键服务的最低水平，最后比较长期目标。
2. 长期目标之间的权重或词典序必须由人类策略显式给出并版本化。求解器不得使用未声明的隐含权重。
3. 没有方案满足前两级时，必须输出：冲突的约束集合、每个降级选项牺牲了什么、各自的证据。由授权者选择，不得自动放宽。
4. **"更好"与"不劣于"必须预登记**：比较前登记**一个**主要长期目标及其改进阈值，以及关键服务的非劣效界 δ（例如关键服务 `T_s` 的乘积极限下分位数之差不小于 −δ）。其余目标只作探索性结果：做多重比较校正（例如 Holm），或明确标注"未校正"，都不得用来主张"更好"。声明多个连续目标、再从中挑出一个点估计更好的，不构成"更好"。
5. 终端状态（§2.1）参与比较：终端约束不满足的方案不满足第一级；没有终端约束时，终端状态必须与长期目标一起列出。

## 6. 扩张核算

### 6.1 扩张提案

一项扩张提案必须声明：

| 字段 | 含义 |
| --- | --- |
| `adds` | 新增的资产与工艺（作为对能力图的增量），描述**投运后**的计划状态 |
| `construction` | 建造所需的资源、能量、占用的资产、时长；它本身也是能力图上的一组目标 |
| `commissioning` | 新工艺计划达到的验证等级（不得低于运营门槛，§6.3）及检验方法 |
| `upkeep` | 维护消耗与维护工艺，按设施寿命或年化核算；时域外到期的大修（例如每 2000 h 更换的耐火内衬）不得因落在 H 之外而消失 |
| `external_inputs` | 建造与维护所需的外部输入清单 |
| `bootstrap` | 建造期间被占用或消耗的、本来用于关键服务的库存和设备 |
| `failure_modes` | 每项新增资产与工艺的故障机制（故障率或 MTBF）及参数来源；合成参数标注 `synthetic`（§6.2） |

补充规则：

- 新增资产与工艺在建造完成前**不存在**；建成但尚未投运时，以其**当前**验证等级参与。未建成的设施没有现场记录，当前等级最高为 `modeled`（§1.5，Physical Ontology §3.5），提案不得把它们声明为更高等级。
- `bootstrap.resources` 是建造消耗中取自关键服务库存的部分。扣除时，同一资源取 `construction.resources` 与 `bootstrap.resources` 中的较大值，不重复计。

### 6.2 净能力增益

净能力增益必须从两个层次评估，在共同外生随机源上对比"扩张"与"不扩张"两条基线：

1. **结构层**：在目标集合 G（由人类策略给出）上，用**运营门槛**评估。运营门槛就是基线运营查询的 `min_verification`，由人类策略给出，不由提案给出。扩张一侧分三个时点评估，都从基线库存中扣除建造与 bootstrap 消耗（§6.1）：
   - **建造期间**：`construction.assets` 与 `bootstrap.assets` 视为不可用，新增内容尚不存在；
   - **建成未投运**：新增内容以当前验证等级参与；
   - **投运后（假设）**：新增工艺与能力按 `commissioning` 声明的等级参与；这一时点的结论必须注明"以投运达到该等级为前提"。

   本地库存不足以支付建造消耗时，提案在该初态下不可建造，必须如实报告，不得改为外部输入了事。每个时点统计：
   - **获得**：由 `blocked` / `unknown` 变为 `candidate` 的目标；
   - **失去**：由 `candidate` 变为任何非 `candidate` 结论（`blocked`、`unknown`、`search_limit`）的目标，按变化后的结论分别列出，例如建造消耗了唯一的备件或原料、占用了唯一的维修机器人；变为 `search_limit` 的还须标注"需加大预算重跑"；
   - **未定**：基线为 `search_limit`（从未判定）的目标发生变化，单独列出，不计为获得。

   获得与失去两个列表都必须报告；不得只报告获得。
2. **时域层**：§4 的四组指标，覆盖建造期与运行期。库存模型必须扣除建造与 bootstrap 消耗，建造期间占用的资产不可用；未扣除的报告不得称为 `modeled_gain`。建造期间关键服务必须满足最低水平，否则提案不予采纳，除非授权者明确接受该风险。
3. **扰动集合**：扩张分支的扰动集合 = 基线扰动集合 ∪ 新增资产与工艺的故障机制（`failure_modes`），用共同外生随机源抽取（§2.3）；新增扰动的参数来源必须报告。否则扩张方案得到的是"新设备永不失效"的乐观偏差。

### 6.3 采纳条件

扩张提案只有同时满足以下条件，才可以被表述为"带来净能力增益"：

1. `commissioning` 声明的等级不低于运营门槛，检验方法已声明，且结构层与时域层都在运营门槛上评估（不得为提案单独降低门槛）。在 `modeled_gain` 阶段，增益以"投运达到声明等级"为前提，必须如实注明；`demonstrated_gain` 及以上要求新工艺实际达到该等级；
2. 结构层三个时点的"失去"列表中都没有关键服务的恢复目标，或每一项都已被授权者明确接受；
3. 时域层在关键服务上不劣于不扩张基线（非劣效界 δ 预登记），且在预登记的唯一主要长期目标上超过预登记的阈值（§5 第 4 条）；
4. 所有未闭合的外部依赖已列出；
5. 结论附带完整的复现清单（§7）。

### 6.4 增益声明等级

| 等级 | 依据 |
| --- | --- |
| `proposed` | 只有提案 |
| `modeled_gain` | 模型与仿真满足 §6.3 |
| `demonstrated_gain` | 新设施实际建成，并有运行记录 |
| `verified_gain` | 在规定运行期内按规定方法确认增益 |

## 7. 报告与复现清单

每份可行性或扩张报告必须附带：

- 输入哈希：初态、场景集合、模型、策略、本契约版本；
- 场景集合的划分：开发集与留出集，以及留出集是否在开发中被查看过。留出集为空或已被查看时，结论只能表述为"开发集结果"；
- 所有运行，包括失败、超时、不可行与数值失败，不得只报告成功运行；这些运行按 §4 计入分布；
- 查询级结论（§3.2 的聚合规则）及每个类别的场景数；
- 随机种子、求解器版本与设置、实际计算消耗。种子与场景集合必须在运行前登记（例如把它们的哈希写入预登记文件）；换一组种子重跑整组也是一次运行，必须报告一共抽取过几组种子及每组的结果；
- 决策记录与终端状态（§2.1）；
- 指标定义的版本；
- 置信区间及其计算方法：抽样方法必须给出；`enumerated` 在有限集合上不适用置信区间，报告须写明"不适用"，而不是留空；有限样本不得表述为鲁棒保证。

## 8. 对照与消融

与 Poieweave 研究纲领 §8.2 一致：

1. 基线至少包括任务优先级策略、带安全库存的规则策略、短期资源优化。
2. 各策略使用相同的初态、观测权限、动作集合、设备模型、扰动机制与计算预算。
3. 逐项移除长期时域、退化模型、能力依赖与重规划，报告各自的贡献。
4. 与多个基线、多个消融比较时，主判定只能基于预登记的主要指标与阈值（§5 第 4 条）；其余比较作为探索性结果，做多重比较校正或标注"未校正"。

## 9. 与其他契约的接口

- 资源、单位、验证等级、能力图查询结论：来自 Physical Ontology。
- 初态引用的状态版本、仿真分支隔离：来自 State & Action Protocol。
- 可行性分析产生的计划只能作为 `proposed` 动作进入协议。

## 10. 待决问题
