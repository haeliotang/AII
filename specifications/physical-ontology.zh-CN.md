# Poieweave 契约一：Physical Ontology（物理运营本体）

版本：0.3-draft / 2026-10-31
状态：可反驳草案。参考实现见 `crates/poie-ontology`，参考场景见 `scenarios/base-01`。接口尚未冻结。

相关契约：[State & Action Protocol](state-action-protocol.zh-CN.md) · [Viability & Expansion](viability-expansion.zh-CN.md)

## 0. 目的与范围

本契约规定 Poieweave 中"物理世界里有什么、能做什么、凭什么这么说"的最小共享语义：

- 标识、物理量与单位；
- 资产、资源、库存批次、工艺、能力、服务等核心实体；
- 生产能力图（capability graph）的结构与求解语义；
- 守恒校验与已知/未知的区分。

不在本契约范围：动作生命周期与网络分区（见 SAP）、长期可行性与扩张核算（见 VEC）、具体设备协议映射、时间调度。

### 0.1 规范用语

"必须"= MUST，"不得"= MUST NOT，"应当"= SHOULD，"可以"= MAY。未使用这些词的句子是说明，不是要求。

## 1. 标识

1. 每个实体必须有全局唯一、稳定的标识，形式为 `<slug>`，其中 slug 匹配 `[a-z0-9][a-z0-9._-]*`。实体类别由所在集合决定（资产、资源类型等），不同类别之间的标识可以重名但不应当重名。
2. 标识一旦被事件引用，不得重新指向另一个物理对象。设备更换后应当分配新标识，并以关系记录"替换了谁"。
3. 仿真分支中的实体沿用现场标识，但所属命名空间必须不同（见 SAP §7）。

## 2. 物理量与单位

### 2.1 量纲

物理量 = 数值 + 量纲。量纲用 7 个 SI 基本量的整数指数表示：长度 L、质量 M、时间 T、电流 I、温度 Θ、物质的量 N、发光强度 J。

1. 规范内部表示必须换算为 SI 相干单位存储（米、千克、秒、焦耳、瓦等）。
2. 不同量纲的量不得相加、相减或比较。功率（W）与能量（J）、流量（m³/s）与体积（m³）因量纲不同而自动区分。
3. 离散物品数量使用无量纲单位 `item`。无量纲量之间的混用由资源类型防止：不同资源类型的数量不得直接相加。
4. v0.2 只支持比例换算（`value_si = value × scale`），不支持带偏移的单位（如 °C、°F）。温度必须用 K 表示。

### 2.2 v0.2 单位表

| 单位符号 | 量纲 | 换算到 SI |
| --- | --- | --- |
| `item` | 1 | 1 |
| `kg` / `g` | M | 1 / 1e-3 |
| `m` / `mm` | L | 1 / 1e-3 |
| `m3` / `L` | L³ | 1 / 1e-3 |
| `s` / `min` / `h` / `d` | T | 1 / 60 / 3600 / 86400 |
| `J` / `kJ` / `MJ` / `kWh` | M·L²·T⁻² | 1 / 1e3 / 1e6 / 3.6e6 |
| `W` / `kW` | M·L²·T⁻³ | 1 / 1e3 |
| `m3/h` | L³·T⁻¹ | 1/3600 |
| `K` | Θ | 1 |

不在表中的单位必须被拒绝，不得猜测。新增单位通过修订本表完成。

### 2.3 数值比较

物理量比较必须使用预先声明的容差。参考实现采用相对容差 1e-9 加绝对容差 1e-12（SI 单位），只用于消除浮点舍入，不代表测量精度。测量不确定性属于证据（§4），不得用放宽容差来掩盖。

## 3. 核心实体

### 3.1 Asset（资产）

有身份、可被占用或维修的物理对象：设备、机器人、母线、工位。

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `id` | 必须 | 标识 |
| `kind` | 必须 | 类别，如 `pump`、`lathe`、`robot`、`power-bus` |
| `status` | 必须 | `available` / `degraded` / `failed` / `unknown` |
| `status_evidence` | 应当 | 支撑该状态的证据记录标识 |
| `requires` | 可以 | 支撑资产列表：本资产可用的前提（如车床依赖母线） |
| `requires_any` | 可以 | 替代支撑资产列表：其中至少一个可用即可（如主电源或应急电源） |
| `degraded` | 可以 | 降级使用策略：`occupiable`、`allowed_processes`、`max_occupations`；缺省时 `degraded` 一律不可占用（见 §6.3 规则 11） |
| `capability_verification` | 可以 | 对所提供能力的验证等级（能力 → 等级）；未声明的能力视为 `declared`（见 §3.6、§6.3 规则 13） |
| `provides` | 可以 | 本资产在可用时提供的能力标识列表 |

状态语义：

- `available`：最近的有效证据表明可以按设计用途使用。
- `degraded`：仍在运行但性能或可靠性下降。缺省情况下不可被工艺占用，也不能作为服务支撑或资产支撑，需先恢复。若资产声明了 `degraded` 策略且允许，可被指定工艺占用（占用次数受策略限制，见 §6.3 规则 11）；但降级占用不等于恢复：报告必须标出使用降级资产的步骤，服务支撑与资产支撑仍要求该资产恢复为可用。
- `failed`：已知不可用。
- `unknown`：没有有效证据，或证据已过期。`unknown` 不得被解释为 `available`。

**可用性是递归的**：一个资产只有当满足以下全部条件时，才可被占用：

1. 自身为 `available`（`degraded` / `failed` 需先恢复，见 §6.3）；
2. `requires` 中的所有资产都可用（AND 关系）；
3. 若 `requires_any` 非空，其中至少一个资产可用（OR 关系）；与 `requires` 同时声明时两者都须满足。

`requires` 与 `requires_any` 共同构成的关系必须无环，模型加载时必须检查；`requires_any` 中不得出现重复项，也不得包含本资产自身。一个资产可以同时没有 `requires` 和 `requires_any`，此时它只依赖自身状态与证据。

### 3.2 ResourceType（资源类型）

可计量、会被消耗或产出的东西：材料、备件、能量、水、废料。

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `id` | 必须 | 标识 |
| `unit` | 必须 | §2.2 中的单位；决定该资源数量的量纲 |
| `mass_per_unit` | 可以 | 每单位质量（kg），用于守恒校验 |

同一物理物品的不同质量状态必须是不同资源类型。例如未检验的加工件 `sleeve-p1-raw` 与检验合格的 `sleeve-p1` 是两种资源，二者之间只能通过检验工艺转换。这样质量门在图结构中是显式的，不是隐藏的标志位。

### 3.3 Lot（库存批次）

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `id` | 必须 | 批次标识 |
| `resource` | 必须 | 资源类型 |
| `quantity` + `unit` | 必须 | 数量；量纲必须与资源类型一致 |
| `quality` | 必须 | `accepted` / `quarantined` / `rejected` |
| `location` | 可以 | 存放位置 |
| `evidence` | 应当 | 最近一次盘点或称重的证据记录 |

只有 `accepted` 的批次可以分配给工艺。`quarantined` 和 `rejected` 必须计入报告，但不得计入可用量。

储存的能量（如电池中的电能）按资源批次建模，单位为能量单位；电池本身作为资产建模。v0.2 不建模充放电功率上限与时间，见 §8。

### 3.4 Process（工艺 / 过程）

一次能把输入变成输出、或把资产恢复为可用的过程。它是能力图中的超边。

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `id` | 必须 | 标识 |
| `inputs` | 可以 | 消耗的资源与数量；执行后从库存中扣除 |
| `outputs` | 可以 | 产出的资源与数量，包括废料流 |
| `yield` | 可以 | 保守合格率：`{ output, fraction, reject }`；见 §6.3 规则 12 |
| `occupies` | 可以 | 执行期间占用、但不消耗的资产 |
| `requires_capabilities` | 可以 | 需要的能力；至少一个提供该能力的可用资产必须存在 |
| `restores` | 可以 | 执行成功后恢复为 `available` 的资产 |
| `duration` | 应当 | 名义时长（时间量纲） |
| `verification` | 必须 | 验证等级，见 §3.5 |
| `asset_mass_change` | 可以 | 进入（正）或离开（负）资产的质量，见 §5 |
| `mass_tolerance` | 可以 | 守恒校验的相对容差，见 §5 |

`outputs` 与 `restores` 至少有一项非空。工艺不得占用它自己要恢复的资产（那必然构成循环依赖），模型加载时必须拒绝。

### 3.5 验证等级

"模型里存在一条路线"不等于"现场能做到"。每个工艺必须声明验证等级，等级依次递增：

| 等级 | 含义 |
| --- | --- |
| `declared` | 有人声称可行，没有模型或试验支撑 |
| `modeled` | 有经过审查的模型或计算支撑 |
| `demonstrated` | 在相同或代表性条件下做成功过至少一次，有记录 |
| `verified` | 在本场址以规定检验方法重复完成，结果可追溯 |

能力图查询必须携带最低验证等级 `min_verification`。低于该等级的工艺不得出现在候选路线中，并必须作为阻断原因报告。

### 3.6 Capability（能力）

在明确条件下完成某类工作的能力，例如 `bearing-replacement`、`precision-turning`。能力由资产提供（`provides`）、被工艺要求（`requires_capabilities`）。自 v0.2 草案起，**能力本身带验证等级**：资产可以在 `capability_verification` 中为它提供的能力声明等级（例如机器人"会换断路器"是否经过演示）。未声明的能力按最弱等级 `declared` 处理。工艺的验证等级说明"这条流程被验证到什么程度"，能力的验证等级说明"这台资产被验证到能做这件事到什么程度"，两者取较低者才是该步骤实际可声明的等级。

### 3.7 Service（关键服务）

人类定义的必须维持的功能，例如供水、生命支持供电。

| 字段 | 要求 | 含义 |
| --- | --- | --- |
| `id` | 必须 | 标识 |
| `requires` | 必须 | 服务成立所需的资产（全部可用） |

v0.2 的服务只是结构性条件（"所需资产都可用"），不含产量或质量指标。服务水平、服务损失积分属于 VEC。

### 3.8 时间（v0.3 草案，M5.1–M5.2）

时间是显式维度；时间值以 SI 秒表示。本节只规定"状态随时间变化"与"工艺实例的调度可行性"，完整时域仿真、能量/功率与可重放属于 M5.3–M5.5。

1. **状态时间线**：资产状态由带时间的状态变更序列描述。某时刻的状态取该时刻之前（含）最近一次变更；没有变更时取初始状态。
2. **预测失效**：预测可以给出失效时间窗口 `[from, to]`。窗口内状态为"预测失效"——这是警告，不是事实；窗口结束仍无新证据时状态为 `unknown`。显式状态变更（证据）优先于预测，预测不得覆盖证据。
3. **库存时间线**：库存由带时间的增减序列描述；任意时刻的可用量 = 初始量 + 该时刻之前的累积变化。计划不得使任何时刻的可用量为负；负值必须作为冲突报告。
4. **工艺实例**：一次工艺执行有开始时间、时长与占用资产；`runs` 次运行按连续占用处理，时长为 `duration × runs`。
5. **调度可行性**：每个被占用资产默认容量为 1；同一资产上的重叠占用是 `capacity_conflict`，必须报告，不得静默串行化。前置关系必须无环；最早开始调度是第一个参考算法，时间可行计划与冲突列表并列输出。
6. **边界**：调度只检查时间与容量，不检查执行。结构候选仍是 `candidate`，时间可行计划不是执行承诺。

### 3.9 能量与功率（v0.3 草案，M5.3）

1. 储能设备有容量、当前荷电状态、最大充电功率与最大放电功率；能量以 SI 焦耳表示，功率以瓦表示。
2. 充放电请求按"功率上限 × 持续时间"以及容量/荷电状态裁剪；任何裁剪都必须报告原因（功率上限、已满、已空），不得静默丢弃。
3. 光伏等发电以固定时间轨迹（每时段的发电量或功率）表达；天气与辐照轨迹是外部输入，必须显式列出。
4. 能量不计入质量守恒（§5）；能量平衡单独核算。v0.3 只要求功率与容量裁剪，完整能量平衡属于后续版本。

### 3.10 离散事件仿真（v0.3 草案，M5.4）

1. 事件按 `(时间, 序列)` 确定性排序；同一输入必须产生同一事件日志（可重放性的基础，见 M5.5）。
2. 扰动轨迹有两类：**固定轨迹**是预排事件；**状态相关轨迹**是声明式规则（条件、延迟、效果），按声明顺序评估，每条规则最多触发一次。
3. 每次内部转化（transfer）必须做质量守恒校验，容差规则同 §5；外部输入/输出以 `external` 流显式记录，不参与内部平衡。
4. 仿真结果包含事件日志、外部流、守恒违规与终态。逐位重放还要求固定模型版本、种子与事件顺序（M5.5）。

### 3.11 时间版场景与结论类别（v0.3 草案，M5.5–M5.6）

1. **时间版场景** = 结构模型 + 资产/库存时间线 + 预登记用例。时间线只描述状态与库存随时间的变化，不改变结构模型本身。
2. **用例**指定：目标、最低验证等级、开始时刻、可选截止时刻。截止时刻可以是显式时间，也可以是"目标所依赖资产中最早的预测失效窗口起点"（`prediction`），用于表达"能否在预测失效前修好"。
3. **结论类别**在结构结论之上增加：`too_late`（有路线，但完成晚于截止）、`insufficient_resource`（步骤开始时刻可用量不足）、`capacity_conflict`（资产被重叠占用）。结构结论为 `blocked` / `unknown` / `search_limit` 时，时间结论与之一致。
4. **资源检查**：按调度顺序累计每个步骤的消耗，并在该步骤开始时刻用库存时间线判断可用量；不得用未来的补给来补足当前步骤。能量与物质资源使用同一规则。
5. **可重放**：确定性输入（结构模型版本、时间线、用例）必须产生相同的执行摘要（digest）。实现必须提供生成与校验摘要的模式，并在 CI 中逐位校验（M5.5）。

## 4. 证据与已知性

本节给出最小要求，记录格式见 SAP §2。

1. 观测（observation）、估计（estimate）、预测（prediction）必须是不同类型的记录，不得互相覆盖。
2. 每条进入状态的关键记录至少携带：来源、事件时间、接收时间、质量标记、模式版本；估计和预测还必须携带模型版本。
3. 状态没有有效证据时为未知（`unknown`）。缺失的数量不得被当作零，缺失的健康状态不得被当作正常。
4. 证据有效期由策略规定。过期证据支撑的状态必须降为 `unknown`，而不是沿用最后的取值。

## 5. 守恒校验

1. **参与范围**：质量校验只针对物质类资源。量纲为能量的资源不参与质量求和。量纲为质量的资源（单位 kg、g）的质量即其数量，无需 `mass_per_unit`；其他物质类资源（如 `item`、`m3`）必须声明 `mass_per_unit` 才能参与校验。
2. **进出资产的质量**：维修类工艺会把零件、润滑脂装进资产，或把旧件从资产中拆出。这部分质量必须用工艺字段 `asset_mass_change`（质量量纲，可为负）显式记账：装入为正，拆出为负。被拆下的旧件作为输出资源记录。
3. **守恒条件**：|Σ输入质量 − Σ输出质量 − `asset_mass_change`| ≤ `mass_tolerance` × max(Σ输入质量, Σ输出质量)。`mass_tolerance` 缺省为 0.01（1%），只用于覆盖测量与取整，不得用来隐藏未建模的损耗。损耗必须作为废料输出显式建模。
4. 若任何物质类资源缺少 `mass_per_unit`，结果必须报告为 `unchecked`，不得报告为通过。
5. 能量不要求与质量一同守恒校验；v0.2 只要求工艺的能量消耗被显式列为输入，因此所消耗的储能会在库存中扣除。完整能量平衡属于后续版本。
6. 模型加载时必须对每个工艺执行守恒校验；`violated` 的工艺必须阻止模型加载。

## 6. 能力图语义

### 6.1 结构

能力图是一个有向超图：

- 节点：资源类型、资产、服务。
- 超边：工艺。尾部 = `inputs` ∪ `occupies` ∪ `requires_capabilities` 的提供者；头部 = `outputs` ∪ `restores`。
- 同一工艺内的所有条件是 **AND**；能产出同一资源或恢复同一资产的不同工艺之间是 **OR**。

首版用显式工艺节点与输入/输出关系实现，不要求专用图数据库。

### 6.2 目标

查询目标（goal）有三类：

| 目标 | 含义 | 满足条件 |
| --- | --- | --- |
| `obtain(r, q)` | 获得 q 数量的资源 r | 从 `accepted` 库存分配，不足部分由产出 r 的工艺补齐 |
| `restore(a)` | 让资产 a 可被占用 | a 已可用（含递归支撑），或执行一个 `restores` 包含 a 的工艺，并满足 a 的支撑资产 |
| `service(s)` | 让服务 s 成立 | `s.requires` 中的每个资产都满足 `restore` |

### 6.3 求解规则

求解器在一张**单一账本**上为目标构造候选路线。账本记录当前路线已经分配的库存和已经恢复的资产。

1. **消耗不重复**：同一份库存在一条候选路线中只能被分配一次。工艺的产出加入账本，可以被同一路线中后续步骤使用。
2. **占用不消耗**：被 `occupies` 的资产在路线中可以多次使用。v0.2 不检查并发、容量与时间冲突，因此结果只是**结构候选**，不是可调度计划。
3. **递归可用性**：占用资产前必须对其求 `restore`，包括其 `requires` 链。
4. **能力要求**：每个 `requires_capabilities` 必须由至少一个可恢复的资产提供；求解器依次尝试提供者。
5. **循环依赖**：若某目标在求解自身的过程中再次出现（例如修复车床需要只能由该车床加工的零件），该分支必须判为阻断，原因为 `cycle`，并报告循环路径。不得假定"先修好再用"。
6. **OR 分支回溯**：尝试某个替代工艺失败时，必须回滚该分支对账本的全部修改，再尝试下一个替代。
7. **验证等级过滤**：低于 `min_verification` 的工艺不参与求解，但必须作为阻断原因记录。
8. **搜索界限**：求解器必须有显式深度上限。达到上限时结果为 `search_limit`，不得当作不可行。
9. **替代支撑（OR）**：资产的 `requires_any` 非空时，求解器必须依次尝试其中的替代资产；任一可用即满足该条 OR 条件。某个替代失败时，必须回滚该尝试对账本的全部修改，再尝试下一个（与规则 6 相同）。全部替代都不可用时，必须报告 `no_alternative_support`，并保留每个替代各自的阻断原因。`requires` 与 `requires_any` 同时存在时必须同时满足。
10. **多来源补足**：一次 `obtain` 的缺口可以由多条产出该资源的工艺分别补足一部分。求解器必须先尝试由单条工艺补足整个缺口（允许重复运行该工艺）；若没有单条工艺能做到，再按模型声明顺序逐次运行一条工艺的一个批次，直到缺口补足或没有任何工艺能再推进。组合过程同样使用单一账本并遵守回溯规则：失败尝试不得修改账本。组合失败时，必须报告各工艺的阻断原因，不得把部分补足报告为 `candidate`。
11. **降级占用（策略）**：资产的状态为 `degraded` 且声明了 `degraded` 策略时，只有当策略 `occupiable` 为真、且（若 `allowed_processes` 非空）当前工艺在列表内，求解器才可以跳过恢复而直接占用该资产。该资产的 `requires` 与 `requires_any` 仍必须满足。每次占用计入该候选路线的占用计数：若声明了 `max_occupations`，同一路线上的累计占用不得超过上限，超过时必须报告 `degraded_restriction`，不得静默多占用。降级占用不写入"已恢复"集合，因此每次占用都要重新检查策略。不允许降级占用的工艺仍需先恢复该资产。
12. **保守合格率与返工**：工艺可以声明 `yield = { output, fraction, reject }`。此时该工艺的 `output` 资源每次运行的合格产出按 `fraction` 计入账本，其余 `1 − fraction` 以 `reject` 资源的形式计入，二者都必须在步骤产出中可见。求解器按 `ceil(需求 / (单次产出 × fraction))` 计算运行次数，缺货补足与多来源组合也使用该有效产出率；不得按 1:1 的确定性产出规划。返工路线由普通工艺表达（消费 `reject` 资源、产出原料或半成品），求解器与其他工艺同等对待。模型加载时必须校验：`fraction ∈ (0, 1]`；`output` 属于该工艺的 outputs；`reject` 与 `output` 的单位及单位质量一致，且 `reject` 不得同时出现在声明的 outputs 中。本条只规定确定性期望合格率，概率分布与统计置信不属于本契约（见 VEC）。
13. **能力验证等级**：工艺的 `requires_capabilities` 中每个能力必须由至少一个提供者满足，且该提供者对此能力的验证等级不得低于查询的 `min_verification`；未声明的能力等级视为 `declared`。低于要求的提供者不得被选中；若全部提供者都低于要求，必须报告 `capability_below_verification`，并保留每个提供者的等级。候选路线的最低验证等级必须同时考虑工艺等级与所选能力的等级（见 §6.4）。
14. **多候选路线枚举**：求解器可以提供一次查询的多个结构候选路线（上限 k）。枚举必须：(a) 去重，同一条路线只出现一次；(b) 为每条路线给出资源消耗、外部依赖与最低验证等级；(c) 有界且确定：必须声明搜索上限，达不到 k 时返回已找到的路线，不得声称穷尽全部结构候选；(d) 只做结构候选，不检查时间、容量与并发。排序与选择准则不属于本契约（见 §8.8、VEC）。
15. **外部依赖上溯**：对一次查询，报告必须给出该查询依赖的全部外部资源（§6.5），做法是：对全部已枚举候选路线的消耗取并集（包括刀具、量具等间接消耗品）；当没有候选路线时，回退到阻断根因中指向外部资源的 `missing_resource`。每条依赖必须标出它出现在哪些路线（或根因）中，以及单条路线上的最大消耗量；报告必须把外部依赖与"本地能做但条件不足"区分开，不得只报告当前这一条路线。

### 6.4 查询结果

| 结论 | 含义 |
| --- | --- |
| `candidate` | 找到一条满足账本约束的结构候选路线。不代表时间、容量或执行上可行。 |
| `blocked` | 在给定模型、库存与验证等级下，所有替代都被确定的原因阻断。不代表物理上不可能，只代表本模型内无路线。 |
| `unknown` | 没有候选路线，且至少一个阻断原因来自未知状态；补齐证据后结论可能改变。 |
| `search_limit` | 达到搜索界限，结论未定。 |

结果必须附带：

- `candidate`：有序的工艺步骤；每一步的库存分配与资产占用；路线的最低验证等级——对每一步取"工艺等级与所用能力等级中的较低者"，再对全部步骤取最低。`candidate` 仍是结构候选：时间与容量可行性由 §3.8 的调度单独检查（§3.11 的时间版场景），也不代表执行承诺。
- 非 `candidate`：完整的阻断原因列表。原因类型至少包括：
  - `missing_resource`：资源、需要量、可用量，且没有可用的生产工艺；
  - `asset_unavailable`：资产及其状态，且没有可用的恢复工艺；
  - `unknown_state`：状态未知的资产；
  - `cycle`：循环目标路径；
  - `below_verification`：被过滤的工艺及其等级；
  - `no_capability_provider`：能力及其候选提供者；
  - `no_alternative_support`：资产的替代支撑列表，以及每个替代各自的阻断原因；
  - `degraded_restriction`：被策略限制的降级资产、已占用次数与上限；
  - `capability_below_verification`：能力、提供者及其验证等级与要求的差距；
  - `depth_exceeded`：达到上限时的目标。

阻断原因应当可以追溯到根因。例如当机器人充电桩和车床都依赖同一条故障母线时，报告应当能让读者看到同一个 `power-bus` 出现在多条分支的根部。

### 6.5 外部依赖

在给定模型中**没有任何本地生产工艺**的资源类型，是该模型的外部依赖。查询结果中出现的 `missing_resource` 若指向外部依赖资源，报告应当标注为"需要外部输入"，以便与"本地能做但条件不足"区分。

单个 `missing_resource` 只说明某一条路线缺什么，不足以支撑"这个服务依赖哪些外部输入"的判断。报告必须按 §6.3 规则 15 做上溯：把一次查询的全部候选路线（无候选路线时为阻断根因）涉及的外部资源汇总成清单，并标注每条依赖出现的路线与最大消耗量。间接消耗品（刀具、量具、润滑脂等）只要在路线上被消耗，就必须计入。

## 7. 与外部标准的关系（说明性）

- Eclipse BaSyx / AAS：资产身份和属性可以映射到 AAS 子模型；本体的 `status`、`requires`、`provides` 与验证等级尚无标准子模型对应，需要定义扩展。
- Eclipse Ditto：Thing 的 features 可以作为观测来源；Ditto 中的期望状态对应 SAP 中的 desired-state 记录，不对应本体中的 `status`。

这些映射尚未实现，也未做兼容性测试。

## 8. 已知局限与待决问题

v0.2 与 v0.3 已解决的条目已并入正文，不在本清单中：替代支撑（§3.1、§6.3 规则 9）、多来源补足（规则 10）、降级占用（§3.1、规则 11）、保守合格率与返工（§3.4、规则 12）、能力验证等级（§3.6、规则 13）、候选路线枚举（规则 14）、外部依赖上溯（§6.5、规则 15）、时间维度的状态/库存时间线、预测失效、工艺实例与调度可行性（§3.8）、能量/功率裁剪（§3.9）、离散事件仿真与守恒核算（§3.10）、时间版场景与结论类别（§3.11）。以下为仍未解决的问题：

1. **能量**：§3.9 只做功率与容量裁剪；完整能量平衡、效率曲线、热管理与发电的物理模型（weather/irradiance 轨迹之外）仍未建模。
2. **操作者技能衰减、工具磨损**：能力本身的验证等级已由 §3.6 支持，但技能随时间的衰减与工具磨损尚未建模。
3. **随机合格率与统计置信**：§3.4 只规定确定性期望合格率；概率分布、返工次数上限与置信区间属于 VEC 时域层。
4. **降级使用的范围**：`degraded` 策略目前只覆盖"占用"；降级资产作为服务支撑或资产支撑仍需先恢复，扩展到这些角色留待后续版本。
5. **候选路线排序与随机扰动**：枚举（§6.3 规则 14）是有界的，不保证穷尽；排序准则不属于本契约。时间版运行当前没有随机源，种子与随机扰动轨迹留待引入。
